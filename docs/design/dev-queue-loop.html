1 · ไอเดียแกน

ปัญหาของ agent loop ทั่วไปไม่ใช่ "เขียนโค้ดไม่เก่ง" แต่คือ ไม่มีนิยามของคำว่าเสร็จ. ralph วน prompt เดิมไปเรื่อย ๆ แล้วประเมินเองว่าพอหรือยัง — ซึ่งแปลว่าเงื่อนไขจบอยู่ในหัว agent, มองไม่เห็น, ตรวจไม่ได้, และเลื่อนได้ตลอด

Dev queue loop ย้ายเงื่อนไขจบออกมาข้างนอก: งานที่ยังไม่จบ = แถวของใบงานบนดิสก์ที่นับได้ คิวว่าง = จบ. ไม่ใช่การตัดสินใจ แต่เป็นการนับ

Ralph loopDev queue loop
หน่วยของงานprompt ก้อนเดียวไม่เปลี่ยนใบงานที่แตกไว้แล้ว หยิบทีละใบ
เงื่อนไขจบagent ประเมินเองคิวว่าง — ตรวจได้ด้วยตาคน
ความคืบหน้าดูไม่ออกจนกว่าจะเปิดดู3/8 ใบ done, 1 blocked
เจอปัญหากลางทางวนแก้ในบริบทเดิมจนงงใบนั้น needs_attention ใบอื่นเดินต่อ
Rollbackต้องแยก diff เองว่าอันไหนของรอบไหน1 ใบ = 1 branch = 1 PR

1.1 กฎที่ทำให้ทั้งระบบไม่พัง

loop เติมงานเข้าคิวเองไม่ได้. คิวถูกเขียนโดยคน (หรือโดยรอบวางแผนที่มีคนอยู่ด้วย) เท่านั้น. ถ้า loop เขียนงานใหม่ให้ตัวเองทำได้เมื่อไร มันกลับไปเป็น open-ended ทันที — ไม่มีเพดาน ไม่มีวันจบ และขอบเขตขยายโดยไม่มีใครอนุมัติ

สิ่งที่ loop ทำได้เมื่อเจองานข้างเคียง คือหย่อนลง proposed[] ซึ่งเป็นถังที่ ไม่มีวันถูกหยิบมาทำในรอบนี้ — เอาไว้ให้ต่องอ่านตอน loop จบแล้วตัดสินว่าจะโปรโมทเข้าคิวรอบหน้าไหม. นี่คือเส้นแบ่งระหว่าง "รอบคิด" กับ "รอบทำ":

  • รอบคิด (มีคนอยู่) — แตกงาน, เคาะ design, เรียงลำดับ, กำหนด acceptance → ผลผลิตคือคิว
  • รอบทำ (ไม่มีคนอยู่) — ทำตามที่เคาะแล้ว จนถึง PR → ผลผลิตคือ PR + รายงาน

Loop จึงไม่ใช่ "ผู้ช่วยที่คิดเองได้" แต่เป็น ตัวขยาย throughput ของงานที่ตัดสินใจไปแล้ว ซึ่งเป็นสิ่งที่มันทำได้ดีจริงโดยไม่ต้องเชื่อใจมันเกินเหตุ

2 · Ticket contract

คุณภาพของ loop นี้ = คุณภาพของคิว ไม่ใช่ความฉลาดของ agent. ใบงานจะเข้าคิวได้ต้องผ่านครบ 4 ข้อ ขาดข้อเดียวคือไม่เข้า:

เกณฑ์แปลว่าถ้าขาด
Acceptance ที่เครื่องตรวจได้ มีคำสั่งที่รันแล้วได้เขียว/แดง — pnpm build, vitest run x.test.ts agent ต้องประเมินเองว่า "ดีพอไหม" = เดา
ไม่มี design decision ค้าง ทางเลือกถูกเคาะมาแล้ว เหลือแค่ลงมือ agent เลือกทางเอง แล้วเดินไปไกลก่อนใครจะทัก
Blast radius รู้ล่วงหน้า บอกได้คร่าว ๆ ว่าจะแตะไฟล์/โมดูลไหน ประเมิน tier ไม่ได้ = คุมความเสี่ยงไม่ได้
ย้อนได้ ผิดแล้ว revert branch จบ ไม่มีผลค้างนอก git ไม่ใช่งานของ loop → ต้องมีคนอยู่ด้วย
เข้าคิวได้

"override transitive dep ให้พ้น GHSA-r28c แล้วให้ build + typecheck ผ่าน"

acceptance = 2 คำสั่ง · ทางแก้เคาะแล้ว · แตะแค่ manifest+lock · revert ได้

เข้าคิวได้

"เพิ่มเทส 3 เคสให้ parseThaiDate ตามตารางในใบ"

เคสระบุครบ · ไม่แตะโค้ดโปรดักชัน · เขียวคือจบ

ห้ามเข้าคิว

"ปรับปรุงระบบ auth ให้ดีขึ้น"

ไม่มี acceptance · design ยังไม่เคาะ · blast radius ไม่รู้ · แตะ RBAC = L3

ห้ามเข้าคิว

"หาสาเหตุที่ prod ช้าแล้วแก้"

debug คืองานที่ต้องคิด ไม่ใช่งานกลไก — และปลายทางแตะ prod

// ใบงาน 1 ใบหน้าตาแบบนี้
{
  "id": "q1",
  "title": "override transitive dep GHSA-r28c",
  "tier": "L2",
  "repo": "acme/acme-app",
  "base": "dev",
  "touches": ["package.json", "pnpm-lock.yaml"],
  "acceptance": ["pnpm install", "pnpm typecheck", "pnpm build"],
  "depends_on": [],
  "status": "todo",
  "attempts": 0,
  "max_attempts": 2
}
ทำไมต้อง max_attempts: ใบที่ลองแล้วไม่ผ่าน 2 ครั้งไม่ใช่ใบที่ "ต้องพยายามอีกหน่อย" แต่คือใบที่เขียนไม่ดีตั้งแต่ต้น — ข้อมูลไม่พอ หรือปัญหาลึกกว่าที่คิด. ลองซ้ำครั้งที่ 3 คือเผา token กับสมมติฐานที่ผิดอยู่แล้ว ให้เด้งเป็น needs_attention ไปเลย

3 · วงจรชีวิตของใบงาน

  todo
    │  หยิบ (WIP=1)
    ▼
  claimed ──────────► blocked_needs_host   (tier L3 / dep ยังไม่ done)
    │  branch + แก้
    ▼
  in_progress
    │  acceptance + autoreview
    ├── ผ่าน ──► pr_open ──(คนกด merge)──► done
    └── ไม่ผ่าน ─┬─ attempts < max ──► todo   (ลองใหม่ tick หน้า)
                 └─ attempts = max ──► needs_attention
statusแปลว่าloop ทำอะไรต่อ
todoพร้อมหยิบหยิบใบบนสุดที่ dep ครบ

blocked_needs_hostL3 หรือรอ depข้าม ไม่แตะเด็ดขาด
donemerge แล้ว—

4 · Invariant 6 ข้อ

ข้อที่ต้องจริงตลอดเวลา ถ้าข้อใดข้อหนึ่งไม่จริงแปลว่า loop พังแล้วแม้จะยังดูเดินอยู่:

  1. WIP = 1 — มีใบสถานะ in_progress ได้ทีละใบเท่านั้น. คาบสองใบ = diff ปนกัน = แยก rollback ไม่ออก
  2. 1 ใบ = 1 branch = 1 PR — หน่วยของงาน, หน่วยของ review, หน่วยของการย้อน ต้องเป็นก้อนเดียวกัน
  3. Persist ก่อน schedule เสมอ — เขียน queue+journal ให้เสร็จก่อนตั้ง wakeup ทุกครั้ง
  4. Fail closed — อะไรไม่แน่ใจ (เทสแดง, review ติด, tier ไม่ชัด) ให้หยุดใบนั้น ไม่ push. loop ไม่มีสิทธิ์ "ปล่อยผ่านไปก่อน"
  5. ไม่มี side effect นอก git ที่ย้อนไม่ได้ — ห้ามส่งเมล ห้ามยิง API จริง ห้าม migrate. PR คือปลายทางสูงสุด
  6. STOP ชนะทุกอย่าง — เจอไฟล์ STOP ตอนต้น tick = จบทันที ไม่ว่ากำลังทำอะไรค้าง

5 · Git model

ทุกใบแตก branch จาก base เดียวกัน (dev) แบบแบน ไม่ stack ต่อกัน:

dev ──┬── loop/q1-dep-override      → PR #201
      ├── loop/q2-date-tests        → PR #202
      └── loop/q4-lint-config       → PR #203

ทำไมไม่ stack: ถ้า q2 แตกจาก q1 แล้วต่องไม่ merge q1 (หรือขอแก้ก่อน) — q2 กับ q3 ที่ต่อยอดมาจะพังตามกันหมด ทั้งที่เนื้องานมันไม่เกี่ยวกันเลย. แบนไว้แปลว่าแต่ละ PR ตัดสินใจอิสระ merge เรียงยังไงก็ได้

แล้วใบที่ขึ้นต่อกันจริง ๆ? ใช้ depends_on — ถ้า dep ยังไม่ done (merge แล้ว) ให้ข้ามใบนั้นไปก่อน ไม่ใช่ไปแตกต่อจาก branch ที่ยังลอยอยู่. ความขึ้นต่อกันเป็นเรื่องของ ลำดับการทำ ไม่ใช่ โครง branch

Base drift: loop ที่วิ่งนานหลายชั่วโมง base จะเคลื่อน (ต่อง merge อย่างอื่นเข้า dev). ก่อนหยิบใบใหม่ทุกครั้งให้ git fetch แล้วแตกจาก origin/dev ล่าสุดเสมอ — ไม่ใช่จาก local ที่ค้างมาตั้งแต่ tick แรก

6 · Crash safety

เซสชันตายกลาง in_progress เป็นเรื่องที่ต้องเกิดแน่ ๆ (เครื่อง sleep, เซสชันปิด, tool error). tick แรกหลังกลับมาต้องทำ reconcile ก่อนหยิบงานใหม่:

  1. เจอใบค้างสถานะ claimed / in_progressดู claimed_at — เกิน stale timeout (เช่น 30 นาที) ถือว่าค้างจริง
  2. ไปดูความจริงที่ git ไม่ใช่ที่ queuebranch ของใบนั้นมีอยู่ไหม, มี commit ไหม, diff ครอบคลุมงานหรือยัง — git คือความจริง queue เป็นแค่สิ่งที่ตั้งใจไว้
  3. ตัดสิน 3 ทางไม่มี branch/diff → คืนเป็น todo · มี diff ครบ → เดินต่อจากขั้น acceptance · diff ครึ่ง ๆ กลาง ๆ ตีความยาก → needs_attention อย่าเดาว่ามันคิดอะไรอยู่
  4. บันทึกเหตุผลที่ตัดสินแบบนั้นลง journalตอนต่องมาไล่ทีหลังจะได้รู้ว่า branch ค้างนั้นมาจากไหน

7 · โหมดพังที่เฉพาะกับเลนนี้

อาการระดับต้นเหตุกัน
Queue poisoning — ใบกำกวมหลุดเข้าคิว แล้ว agent เดา design เองจนได้ PR ที่ผิดทาง สูง เขียนใบตอนรีบ ข้าม ticket contract บังคับ 4 เกณฑ์ตอนเขียนคิว ไม่ใช่ตอน loop วิ่ง — จุดคุมคุณภาพอยู่ที่รอบคิด
Scope creep ในใบ — เจอของข้างเคียงแล้วแก้พ่วงไปด้วย สูง สัญชาตญาณ "เห็นแล้วเก็บให้เลย" เจอ = หย่อนลง proposed[] ห้ามแก้ในใบนี้. diff ต้องตรงกับ touches
Green-washing — ข้ามเทสแดงเพื่อให้คิวเดินสวย สูง ตัวชี้วัด "ใบเสร็จ" ดันให้อยากผ่าน Fail closed + วัด first-pass rate ไม่ใช่จำนวนใบ. รายงานต้องระบุแดง/pre-existing ตามจริง
Dependency deadlock — ทุกใบรอ dep ที่ยังไม่ merge คิวเดินไม่ได้ กลาง เรียงคิวโดยไม่ดู dep ทุกใบ blocked = stop + รายงาน อย่าวนเปล่ารอคนกด merge
Base drift / conflict สะสม กลาง แตก branch จาก local ที่ค้างเก่า fetch + แตกจาก origin/<base> ทุกใบ
PR ท่วม — เปิด 8 PR รวดให้คนรีวิว ต่ำ คิวยาวเกินกำลังรีวิวของคน เพดาน max_open_prs (เช่น 3) ชนแล้ว stop รอเคลียร์

8 · ตัววัด

อย่าวัดว่า loop ทำได้กี่ใบ — วัดว่ามันสร้างงานให้คนเพิ่มหรือลด:

ตัววัดคำนวณเกณฑ์ต่ำกว่าเกณฑ์ = แก้ที่
First-pass rate PR ที่ merge โดยไม่ต้องแก้ ÷ PR ทั้งหมด ≥ 70% ticket contract ไม่ใช่ prompt ของ loop
Escalation rate ใบที่จบด้วย needs_attention/blocked ≤ 25% การคัดใบเข้าคิว — เอางานที่ยังต้องคิดมาใส่
Revert rate PR ที่ merge แล้วต้องย้อน ≈ 0 acceptance อ่อนเกิน — เพิ่มคำสั่งตรวจ
Token / ใบที่ merge token ทั้ง loop ÷ ใบที่ merge จริง เทียบกับทำเอง ถ้าแพงกว่าทำเอง = งานประเภทนั้นไม่ควรเข้า loop
อ่านตัวเลขให้ถูก: first-pass ต่ำ ไม่ได้แปลว่า agent โง่ — เกือบทุกครั้งแปลว่าคิวถูกเขียนหลวมเกินไป. จุดที่ต้องกลับไปแก้คือรอบคิด ไม่ใช่ไปจูน prompt ของรอบทำ
