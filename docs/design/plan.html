Loop AI Workflow

แผน + สถาปัตยกรรมของ loop ที่รันบน Claude Code /loop — ครอบคลุม 3 งาน: เฝ้าสถานะ, dev วนรอบ, สรุปประจำวัน

ข้อสรุปที่ต้องรู้ก่อนอย่างอื่น: /loop dynamic mode มี hard clamp ที่ 60–3600 วินาที ต่อ 1 ช่วงพัก — แปลว่า ทำ daily digest ด้วย /loop ตรง ๆ ไม่ได้ (ต้อง burn ทิ้ง 24 tick/วัน). งานรายวันต้องไปราง /schedule (cron) เท่านั้น. เลน C ในเอกสารนี้เลยออกแบบเป็น cron-triggered ไม่ใช่ loop.

สารบัญ

  1. กลไกที่มีจริง — 4 ราง เลือกยังไง
  2. Shared kernel — state contract + tick protocol
  3. เลน A · Watcher loop (เฝ้าสถานะ/รอผล)
  4. เลน B · Dev queue loop (งาน dev วนรอบ)
  5. เลน C · Digest (สรุปประจำวัน)
  6. Safety — tier gate ใน loop
  7. Failure mode + วิธีกัน
  8. ต้นทุน token
  9. Rollout — ทำอะไรก่อนหลัง

1 · กลไกที่มีจริง — 4 ราง

ทั้ง 4 รางนี้คนละกลไกกัน ไม่ใช่ของอย่างเดียวกันคนละชื่อ เลือกผิดรางแล้วทั้ง design พัง:

รางกลไกช่วงพักได้Contextเหมาะกับ
/loop 5m <cmd>
fixed		 ตั้ง cron ภายใน ยิง prompt เดิมทุก N นาที ตาม interval ที่ตั้ง ต่อเนื่องในเซสชัน งานที่จังหวะรู้ล่วงหน้าแน่ ๆ
/loop <prompt>
dynamic		 โมเดลเรียก ScheduleWakeup เองทุกเทิร์น เลือกเวลาตื่นเอง 60–3600s (clamp) ต่อเนื่องในเซสชัน ค่าเริ่มต้นของทั้ง 3 งาน — จังหวะปรับตามสถานการณ์
/schedule
cron cloud		 agent วิ่งบน cloud ตามตาราง ไม่ต้องเปิดเครื่องค้าง อิสระ (รายวัน/สัปดาห์ได้) เริ่มใหม่ทุกครั้ง — ไม่มี memory ของรอบก่อน daily digest, weekly curate
ralph-loop
stop-hook		 Stop hook บล็อกการจบเทิร์น แล้วป้อน prompt เดิมซ้ำทันที ไม่พัก — ชนกันรัว ต่อเนื่อง (บวมเร็วมาก) grind งานเดียวจนเสร็จ ไม่ใช่ scheduling

ผลของการเลือก

  • เลน A (watcher) + เลน B (dev queue) → /loop dynamic. เหตุผล: จังหวะที่ควรตื่นขึ้นกับสถานะจริง (CI เพิ่งเริ่ม = พัก 8 นาที, CI ใกล้จบ = พัก 90 วิ) fixed interval จะได้ tick เปล่าเยอะโดยเปล่าประโยชน์
  • เลน C (digest) → /schedule. เพราะเกิน clamp และไม่ต้องการ context ต่อเนื่องอยู่แล้ว — มัน re-read จากไฟล์เสมอ
  • ralph-loop ยังไม่ใช้ — มันไม่มี backoff, ไม่มี tier gate, และวนบน prompt เดิมที่ไม่เปลี่ยน. ต้นทุนสูงและคุมยาก. ถ้าอยากได้ dev grind ให้ใช้เลน B ที่มี queue คุมแทน
กฎเหล็กของ dynamic mode: ถ้าสั่งงาน background ไว้ (background Bash, Task) harness จะปลุกให้เองตอนงานจบ — ห้ามตั้ง wakeup สั้นเพื่อ poll งานตัวเอง นั่นคือ tick ทิ้งเปล่า. ตั้ง fallback ยาว (1200s+) ไว้กันงานค้างเงียบเท่านั้น. poll สั้นสงวนไว้ให้ของนอกระบบล้วน ๆ (CI, deploy, คิว remote)

2 · Shared kernel

ทุกเลนใช้ contract เดียวกัน จะได้ debug ที่เดียว เพิ่ม loop ใหม่แล้วไม่ต้องคิดใหม่

2.1 State อยู่บนดิสก์ ไม่ใช่ใน context

นี่คือ design decision ที่สำคัญที่สุดของเอกสารนี้. loop ที่ยาวพอจะโดน compaction เสมอ และ compaction กินรายละเอียดหาย — ถ้า state อยู่ในหัวอย่างเดียว loop จะเริ่มตัดสินใจจากความจำที่ถูกย่อแล้ว. ทุก tick อ่านสถานะจากไฟล์ ไม่ใช่จากที่จำได้ context เป็นแค่ที่ทำงานชั่วคราว

~/.claude/loops/<loop-name>/
├── state.json     # สถานะปัจจุบัน (ต้นทางความจริง)
├── journal.md     # append-only: tick ไหน ทำอะไร ทำไม
├── seen.json      # id ที่จัดการไปแล้ว — กันทำซ้ำ
└── STOP           # ไฟล์ kill switch (มี = จบทันที)
// state.json
{
  "loop": "acme-app-ci-watch",
  "lane": "A",
  "started_at": "2026-08-11T22:10:00+07:00",
  "deadline_at": "2026-08-12T02:00:00+07:00",   // กันวนข้ามคืน
  "tick": 7,
  "max_ticks": 60,                               // budget แข็ง
  "phase": "waiting_ci",                         // state machine
  "target": { "repo": "acme/acme-app", "pr": 128 },
  "last_observed": { "ci": "in_progress", "at": "2026-08-11T22:38:00+07:00" },
  "consecutive_noop": 5,
  "escalations": []                              // สิ่งที่รอต่องตัดสิน
}

2.2 Tick protocol — 6 ขั้น เหมือนกันทุกเลน

  1. Readอ่าน state.json + เช็ค STOP. มี STOP → ScheduleWakeup(stop:true) จบเลย ไม่ทำอะไรต่อ
  2. Guardเกิน max_ticks หรือเลย deadline_at → เขียนสรุปลง journal แล้ว stop. กันวนไม่จบเป็นเงื่อนไขบังคับ ไม่ใช่ทางเลือก
  3. Observeดึงสถานะจริงด้วยคำสั่งที่ถูกที่สุด — gh pr checks บรรทัดเดียว ไม่ใช่อ่าน log ทั้งก้อน. observation ต้องเบา เพราะจะทำอีกหลายสิบครั้ง
  4. Decideเทียบกับ last_observed: ไม่เปลี่ยน → ไม่ทำอะไร. เปลี่ยน → ทำ action ตาม state machine ของเลนนั้น พร้อมเช็ค seen.json กันทำซ้ำ
  5. Persistเขียน state.json ทับ + append journal.md 1 บรรทัด ก่อน ตั้ง wakeup เสมอ — ถ้าเซสชันตายตรงนี้ รอบหน้ายังต่อได้
  6. ScheduleScheduleWakeup พร้อม noop ตามจริง: ไม่มีอะไรเปลี่ยน = noop:true (จอต่องจะยุบบรรทัดพวกนี้ให้เอง), มี action = noop:false

2.3 การเลือกช่วงพัก (backoff)

สถานการณ์delaySecondsเหตุผล
รอของนอกระบบที่รู้เวลาโดยประมาณ (CI ~8 นาที)480เช็ค 1 ครั้งตอนน่าจะเสร็จ ดีกว่าเช็ค 8 ครั้งทุกนาที
เพิ่งเห็นสถานะขยับ กำลังจะถึงจุดตัด60–180ช่วงเดียวที่คุ้มจะถี่
มี background task ทำงานอยู่ (harness ปลุกเอง)1200–1800เป็นแค่ fallback กันงานแฮงก์เงียบ
noop ติดกัน ≥ 3 ครั้ง× 2 จนชน 3600exponential backoff — เงียบนานแปลว่าไม่ต้องขยัน
ไม่มีสัญญาณอะไรให้ดูเป็นพิเศษ1200–1800ค่า default ที่ไม่เผา token

3 · เลน A — Watcher loop

เฝ้าสถานะ / รอผล · L0 read-only

เฝ้า CI, PR review, deploy, คิวงาน — งานที่ 90% ของ tick คือ "ยังไม่มีอะไร" เป้าหมายคือให้ tick เปล่าถูกที่สุดเท่าที่จะถูกได้ และ tick ที่มีของจริงต้องไม่พลาด

State machine

idle → watching → changed → (report) → watching
                     ↘ terminal(success|fail|timeout) → stop
Trigger

สั่งด้วยมือตอนเปิดงาน

เปิด PR เสร็จปุ๊บสั่ง loop เฝ้าต่อ ไม่ต้องนั่งเฝ้าเอง

Action ที่ทำเองได้

อ่าน + รายงาน เท่านั้น

สรุป CI แดงว่าเทสไหนพัง ที่ไฟล์ไหน — แต่ไม่แก้เอง ในเลนนี้

Exit

terminal state หรือ deadline

CI เขียว/แดงสรุปแล้ว, PR merged, หรือเลยเวลาที่ตั้งไว้

ตัวอย่างคำสั่ง

/loop เฝ้า CI ของ PR acme/acme-app#128 — state ที่ ~/.claude/loops/acme-app-ci-watch/
เช็คด้วย gh pr checks เท่านั้น, เขียน state+journal ทุก tick,
เขียว = สรุปแล้ว stop, แดง = สรุปว่าเทสไหนพังที่ file:line แล้ว stop,
deadline 02:00 หรือ 60 ticks
ทำไมแยก watcher ออกจาก dev loop: watcher เป็น read-only ล้วน ปล่อยวิ่งข้ามคืนได้โดยไม่ต้องคิดเรื่องความเสี่ยง. พอไปรวมกับ "แก้เองเลย" เมื่อไร มันกลายเป็นเลน B ทันทีและต้องมี gate — แยกไว้จะได้ไม่เผลอให้สิทธิ์เกิน

4 · เลน B — Dev queue loop

งาน dev วนรอบ · L1–L2 เขียนโค้ดได้ มี gate · อ่านคอนเซปต์เต็ม →

หลักการต่างจาก ralph โดยสิ้นเชิง: ralph วน prompt เดิมจนกว่าจะพอใจ (ไม่มีนิยามของเสร็จ) ส่วนเลนนี้ วนบน queue ที่มีของนับได้ — 1 tick = 1 ใบงาน จบใบแล้วเปิด PR แล้วค่อยหยิบใบถัดไป. คิวหมด = จบ. เห็นความคืบหน้าเป็นตัวเลขตลอด

~/.claude/loops/<name>/queue.json
[
  {"id":"q1","title":"override transitive dep GHSA-r28c","tier":"L2","status":"todo"},
  {"id":"q2","title":"เพิ่ม test coverage utils/date","tier":"L1","status":"todo"},
  {"id":"q3","title":"rotate API key","tier":"L3","status":"blocked_needs_host"}
]

รอบการทำงาน 1 tick

  1. หยิบใบบนสุดที่ status=todoทำทีละใบ ห้ามคาบสองใบ — คาบสองใบแล้ว diff ปนกัน rollback ไม่ได้
  2. เช็ค tier ก่อนแตะโค้ดL3 → mark blocked_needs_host ใส่ escalations แล้วข้ามไปใบถัดไปทันที ห้ามลงมือเอง
  3. Branch + แก้ + targeted testgit checkpoint ก่อนเสมอ, รัน lint/typecheck/unit เฉพาะที่แตะ
  4. autoreviewเทสแดงหรือ review เจอของ → status=needs_attention ไม่ push. อย่ากลบผลแดงเพื่อให้ loop เดินต่อสวย ๆ
  5. push + PR เข้า devmain/prod ไม่แตะเด็ดขาด — PR ค้างไว้ให้ต่องกดเอง
  6. อัปเดต queue แล้ว wakeup สั้นมีของค้าง = 60–120s (ไม่ได้รออะไร รีบทำใบต่อไป), คิวว่าง = stop พร้อมสรุป
เพดานของเลนนี้: ใบงานที่เข้าคิวได้ต้อง ระบุชัดจนไม่ต้องตัดสินใจเชิงออกแบบ ("bump dep + ให้ build ผ่าน", "เพิ่มเทสเคสนี้"). งานที่ต้องออกแบบ/เลือกทาง อย่าโยนเข้าคิว — loop จะเดาแล้วเดินหน้าไปไกลก่อนต่องจะได้ทักท้วง. คิวคือที่ของงาน mechanical ที่ design นิ่งแล้วเท่านั้น

5 · เลน C — Digest

สรุป/กลั่นข้อมูลประจำวัน · L0 · ราง /schedule ไม่ใช่ /loop

รายวันเกิน clamp 3600s ของ /loop อยู่แล้ว และงานนี้ไม่ต้องการ context ต่อเนื่อง — มันอ่านจากไฟล์/ระบบใหม่ทุกครั้ง. /schedule จึงตรงกว่า และได้ข้อดีเพิ่มคือไม่ต้องเปิดเซสชันค้างไว้

เวลางานInputOutput
ทุกวัน 21:00 Daily digest git log วันนี้ทุก repo ที่ทำงาน, PR ที่ขยับ, session capture ของวัน append ลง Daily note ใน Obsidian + fleeting ถ้ามีของใหม่
ศุกร์ 17:00 Weekly curate มีอยู่แล้ว fleeting ที่สะสม อัปเดต memory + proposal
บทเรียนจากของเดิม: cron ที่มีอยู่ (self-upgrade loop) เคยตายเงียบมาแล้ว — cron ไม่มีใครดูแลจะเงียบหายโดยไม่มีใครรู้. ทุก job ของเลนนี้ต้อง เขียน heartbeat ลง ~/.claude/loops/<job>/journal.md ทุกรอบแม้ไม่มีอะไรทำ แล้ว watcher เบา ๆ (หรือ digest ตัวถัดไป) เช็คว่า heartbeat ล่าสุดเก่าเกิน 48 ชม.ไหม. ไม่มีข่าว ≠ ข่าวดี

6 · Safety — tier gate ใน loop

loop คือการให้สิทธิ์ลงมือโดยไม่มีคนดูอยู่ตรงนั้น เพดานสิทธิ์เลยต้องต่ำกว่าตอนคุยกันสด:

Tierในเซสชันปกติใน loop (ไม่มีคนดู)
L0ทำเลยทำเลย
L1ทำเลย + targeted testทำได้ + ต้อง checkpoint ก่อนทุกครั้ง
L2plan + reviewerถึง PR ได้ ห้าม merge — ค้างไว้ให้คนกด
L3ยืนยันเป็นลายลักษณ์ + gateห้ามลงมือทุกกรณี → เข้า escalations อย่างเดียว
  • Classify ไม่ชัด = เด้งขึ้นเลนสูงกว่าเสมอ — ใน loop โทษของการเดาผิดแพงกว่ามาก เพราะไม่มีใครทักระหว่างทาง
  • Kill switch ต้องใช้ได้โดยไม่ต้องคุยกับ agent — touch ~/.claude/loops/<name>/STOP จบใน tick ถัดไปเสมอ ไม่ว่า loop กำลังคิดอะไรอยู่
  • Escalation ไม่ปลุกคน — สะสมใน state แล้วรายงานทีเดียวตอน loop จบ ไม่ยิงเตือนกลางดึก

7 · Failure mode

อาการระดับเกิดเพราะกันยังไง
Loop วนไม่จบ เผา token ทั้งคืน สูง ไม่มีเงื่อนไขจบ หรือเงื่อนไขจบไม่มีวันเป็นจริง max_ticks + deadline_at เป็นฟิลด์บังคับใน state ตั้งแต่ tick แรก
ทำ side effect ซ้ำ (คอมเมนต์ PR ซ้ำ, ส่งซ้ำ) สูง tick ใหม่ไม่รู้ว่า tick ก่อนทำไปแล้ว seen.json — เช็ค id ก่อนทำทุก external action
ตัดสินใจจากความจำที่โดนย่อ สูง compaction กินรายละเอียดกลาง loop อ่าน state จากไฟล์ทุก tick ห้ามเชื่อสิ่งที่ "จำได้"
Loop ตายเงียบ ไม่มีใครรู้ กลาง เซสชันปิด / เครื่อง sleep / cron พัง heartbeat ลง journal ทุก tick + เช็คอายุ heartbeat
Poll ถี่เกินจนเปลืองเปล่า กลาง ตั้ง wakeup สั้นเพื่อรองาน background ของตัวเอง งาน background = harness ปลุกเอง ตั้ง fallback 1200s+ พอ
เทสแดงแต่ loop เดินต่อ กลาง อยากให้คิวเดินหน้า เลยข้ามผลแดง แดง = needs_attention หยุดใบนั้น รายงานตามจริง ไม่ push
State ไฟล์พัง / เขียนไม่ครบ ต่ำ ตายกลางคันตอนเขียน เขียน state ก่อนตั้ง wakeup เสมอ + journal เป็น append-only ไว้ไล่ย้อน

8 · ต้นทุน token

ค่าใช้จ่ายจริงของ loop = จำนวน tick × ราคาต่อ tick ลดได้ทั้งสองทาง:

  • ลดจำนวน tick — backoff แบบ exponential ตอนเงียบ, ตั้ง deadline ให้ตรงความจริง, อย่า poll สิ่งที่ harness ปลุกให้อยู่แล้ว
  • ลดราคาต่อ tick — tick เปล่าควรเป็น "อ่าน state + คำสั่งเช็ค 1 บรรทัด + เขียน 1 บรรทัด" จบ. ห้าม tick เปล่าไปไล่อ่านไฟล์โปรเจกต์
  • Tier ลงเฉพาะงานกลไก — observe/collect ใน watcher เป็นงาน mechanical, ส่วน decide/review คงระดับเต็ม. ลังเลแม้นิดเดียว = ไม่ tier ลง
  • ประหยัดที่ได้เปล่า: เซสชันนี้ prompt cache TTL 1 ชม. ซึ่งครอบคลุมทุกช่วงพักที่ตั้งได้อยู่แล้ว — ไม่ต้องตั้ง wakeup ถี่เพื่อ "keep cache warm" นั่นคือจ่ายเพิ่มเพื่อของฟรี

9 · Rollout

  1. Phase 1 — เลน A ตัวเดียว เริ่มที่นี่ ทำ watcher เฝ้า CI ของ PR จริง 1 ตัว. ได้ของใช้จริงทันที และเป็นที่ทดสอบ kernel (state/journal/backoff/STOP) แบบไม่มีความเสี่ยงเพราะ read-only ล้วน. วัดผล: tick ทั้งหมดกี่ครั้ง, tick เปล่ากี่ครั้ง, พลาดจังหวะไหม
  2. Phase 2 — เลน C ต่อยอด cron เดิม เพิ่ม daily digest 21:00 เข้าราง /schedule ที่มี weekly curate อยู่แล้ว + ใส่ heartbeat ให้ job เดิมด้วย (แก้จุดที่เคยตายเงียบไปในตัว). ยัง L0 อยู่
  3. Phase 3 — เลน B ต่อเมื่อ kernel พิสูจน์แล้วจาก 2 phase แรก. เริ่มด้วยคิว L1 ล้วน 2–3 ใบ ให้จบที่ PR แล้วดูคุณภาพ diff ก่อนขยาย
  4. Phase 4 — ทำเป็น skill พอ pattern นิ่ง ค่อยห่อเป็น skill /loop-watch, /loop-queue จะได้ไม่ต้องพิมพ์ prompt ยาวทุกครั้ง — ตอนนี้ยังไม่ทำ ห่อ pattern ที่ยังไม่นิ่งคือ premature abstraction
