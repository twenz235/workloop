QA Loop + Grooming Skill

ประเมินไอเดียของต่อง 2 ข้อ: แยก QA loop ออกจาก dev loop, และทำ skill แปลง requirement เป็นการ์ด

สรุปคำตัดสิน: ทั้งสองไอเดียถูกทาง และ skill grooming สำคัญกว่า QA loop ควรทำก่อน. ส่วน QA loop มี 1 จุดที่พังแน่ ๆ ถ้าทำตามที่ร่างมา — ไม่ผ่าน → todo ทำให้ dev กับ QA ตีกันไปมาไม่มีวันจบ. อีก 4 จุดเป็นเรื่องต้องนิยามให้ชัดก่อนเริ่ม

1 · QA loop มีค่าตรงไหน

เหตุผลที่ควรมี ไม่ใช่ "เพราะของจริงเขามี QA" แต่เพราะ autoreview ที่รันในบริบทเดียวกับตอนเขียน มันตรวจตัวเองไม่ออก — มันเห็นเหตุผลของตัวเองว่าทำไมถึงเขียนแบบนั้น เลยมีแนวโน้มเห็นด้วยกับตัวเอง. anchoring bias นี้แก้ด้วย prompt ไม่ได้ ต้องแก้ด้วยการเปลี่ยนบริบท

QA ที่ทำงานจาก context สะอาด เห็นแค่ใบงาน + diff โดยไม่รู้ว่า dev คิดอะไรอยู่ตอนเขียน จะถามคำถามที่ dev ไม่ถามตัวเอง: "diff นี้ทำสิ่งที่ใบงานขอจริงไหม" ไม่ใช่ "โค้ดนี้ทำงานตามที่ฉันตั้งใจไหม"

เงื่อนไขที่ทำให้คุ้ม: QA ต้องเป็น fresh context จริง ๆ (subagent แยก หรือ tick ที่อ่านจากไฟล์ล้วน) และตรวจคนละชุดกับที่ dev ตรวจไปแล้ว. ถ้า QA = รัน autoreview ซ้ำอีกรอบในบริบทเดิม = จ่ายสองเท่าเพื่อคำตอบเดิม ไม่ต้องทำก็ได้

2 · 5 จุดที่ต้องแก้

พังแน่ถ้าไม่ครบ 3 ชั้น

2.1  ทางกลับของ QA

ร่างแรกของต่อง: ไม่ผ่าน → todo · ร่างที่แก้แล้ว: ไม่ผ่าน → เขียนคอมเมนต์รายละเอียด → todo

การเติม "เขียนคอมเมนต์รายละเอียด" แก้ถูกจุดที่สำคัญที่สุด — ปัญหาเดิมคือ dev tick หน้าหยิบใบขึ้นมาโดยไม่รู้ว่า QA ติดอะไร เลยทำแบบเดิมอีกแล้วโดนตีอีก. มี finding แล้วรอบถัดไปจะไม่ใช่การทำซ้ำอีกต่อไป

แต่ยังขาดอีก 2 ชั้น ที่จำเป็นเพราะ คอมเมนต์ดีแค่ไหนก็ไม่การันตีว่าจะจบ: ถ้า QA คาดหวังบางอย่างที่ใบงานไม่เคยระบุ มันจะตีกลับด้วย finding ใหม่ได้ทุกรอบ ไม่ซ้ำของเดิมเลยแต่ก็ไม่มีวันจบ

ต้องมีครบ 3 ชั้น:
  • ① finding ที่ actionable ต่องเติมแล้ว — qa_findings[] มี file:line + อ้างข้อของ acceptance + severity (รายละเอียดส่วนที่ 4.1)
  • ② แยกให้ออกว่าใบนี้ "เคยโดนตี" — ปลายทางจะชื่อ todo ก็ได้ ชื่อไม่ใช่ประเด็น แต่ dev ต้องอ่านออกจากการ์ดว่า ต้องแก้ต่อบน branch/PR เดิม ไม่ใช่แตกใหม่ และใบพวกนี้ต้องถูกหยิบก่อนใบใหม่เสมอ. ถ้าใช้ status:"todo" ล้วนแล้วเรียงตามลำดับปกติ ใบที่แก้ค้างจะถูกดองท้ายแถวขณะที่ loop ไปเปิดงานใหม่เรื่อย ๆ
  • ③ เพดานจำนวนรอบ — rework_count สูงสุด 2 ครบแล้วเด้ง needs_attention ให้คน. นี่คือชั้นเดียวที่รับประกันว่าจบ ไม่ว่า finding จะดีแค่ไหน. QA ไม่พอใจหลังแก้ 2 รอบ = ใบงานเขียนไม่ชัดตั้งแต่ต้น ไม่ใช่ dev ทำไม่ได้ — ต้องให้คนมาตัดสิน ไม่ใช่ให้ bot เถียงกันต่อ
ต้องนิยาม

2.2  QA ผ่าน → done เท่ากับให้ bot อนุมัติ merge

ในดีไซน์เดิม done = merge แล้ว ซึ่งคนเป็นคนกด. ถ้า QA ผ่านแล้วเลื่อนเป็น done เลย เท่ากับ QA loop กลายเป็นผู้อนุมัติ — เพดานสิทธิ์ถูกยกขึ้นโดยไม่ได้ตั้งใจ ขัดกฎ "loop ไปได้สูงสุดแค่ PR"

แก้: QA ผ่าน → ready_for_human (พร้อมให้กด). done สงวนไว้สำหรับ merged เท่านั้น และเป็นสถานะเดียวที่ loop เขียนเองไม่ได้ — มันเปลี่ยนได้จากการอ่าน git ว่า PR ถูก merge แล้วเท่านั้น
ต้องนิยาม

2.3  PR เปิดตอนไหน

ถ้า dev เปิด PR ปกติแล้ว QA ตีกลับ → PR ค้างเป็นขยะรอ force-push. ถ้าไม่เปิด PR เลย → QA ต้องอ่าน diff จาก local ซึ่งเสียประโยชน์ของ CI

แก้: dev push branch + เปิด draft PR ตอนเข้า in_review — CI ได้รัน, QA อ่าน diff จาก PR ได้, และมันประกาศตัวว่ายังไม่พร้อม. QA ผ่าน → gh pr ready. ตีกลับ → dev commit เพิ่มบน branch เดิม ไม่แตกใหม่ (ประวัติการตีกลับจะได้อยู่ใน PR เดียว ตามรอยได้)
ต้องนิยาม

2.4  QA ตรวจอะไรที่ autoreview ไม่ได้ตรวจ

ถ้าไม่แบ่งให้ชัด QA จะกลายเป็น autoreview รอบสอง = ต้นทุนคูณสองโดยไม่ได้ข้อมูลใหม่ แล้วสุดท้ายต่องจะปิดมันทิ้งเพราะรู้สึกว่าไม่คุ้ม

แก้: แบ่งตามตารางในส่วนที่ 4 — dev ตรวจ "ทำงานถูกไหม" (white-box), QA ตรวจ "ทำตรงใบงานไหม + พังของเดิมไหม" (black-box จากใบงาน)
ระวัง

2.5  2 loop เขียน queue ไฟล์เดียวกัน = lost update

ถ้า dev loop กับ QA loop วิ่งคนละเซสชันพร้อมกัน ทั้งคู่จะ read-modify-write queue.json ทับกัน — อันที่เขียนทีหลังลบงานของอีกอันเงียบ ๆ. เคสแบบเดียวกับที่เคยโดนใน vault ตอนสอง session แย่งกัน stage git

แก้: เริ่มด้วย loop เดียว 2 บทบาท (ส่วนที่ 5) ซึ่งไม่มี race เลยเพราะไม่มีอะไรทำงานพร้อมกัน. แยกเป็น 2 loop ต่อเมื่อวัดได้ว่า QA เป็นคอขวดจริง และตอนนั้นค่อยใส่ atomic write + one-writer-per-status

4 · ใครตรวจอะไร

มุมมอง White-box — เห็นโค้ดที่ตัวเองเพิ่งเขียนและรู้ว่าทำไม Black-box — เห็นแค่ใบงาน + diff ไม่เห็นเหตุผลของ dev
คำถามหลัก "โค้ดนี้ทำงานตามที่ฉันตั้งใจไหม" "diff นี้ทำสิ่งที่ใบงานขอจริงไหม และพังของเดิมไหม"
ตรวจ typecheck · lint · unit เฉพาะที่แตะ · autoreview บน diff build/integration เต็ม · เทสชุดเดิมทั้งหมด (regression) · acceptance ทุกข้อในใบทีละข้อ
ตรวจเฉพาะทาง — Scope drift: diff แตะเกิน touches ไหม
Test theater: เทสที่เพิ่มมา assert ค่าจริงหรือแค่ทำให้เขียว
Acceptance ครบ: ใบขอ 3 ข้อ ทำครบ 3 หรือทำ 2
Tier drift: ทำไปแล้วกลายเป็นแตะของ L3 ไหม
ผลลัพธ์ ผ่าน = ได้ push (draft) ผ่าน = ready_for_human · ไม่ผ่าน = findings ที่ file:line
ข้อห้ามของ QA: QA ห้ามแก้โค้ดเองเด็ดขาด แม้จะเห็นว่าแก้แป๊บเดียว. ถ้า QA แก้ได้ มันก็ตรวจงานตัวเองอีก = กลับไปที่ปัญหาเดิมที่ QA ถูกสร้างมาเพื่อแก้. QA เขียนได้แค่ finding เท่านั้น

4.1  คอมเมนต์ที่ดีหน้าตายังไง

"เขียนคอมเมนต์รายละเอียด" เป็นทางที่ถูก แต่มีกับดักซ่อนอยู่ 2 อัน — ละเอียดผิดทางแล้วจะแย่กว่าไม่ละเอียด:

ต้องมีทำไม
file:line dev รอบใหม่ไม่ต้องไล่หาเอง = ประหยัด tick และไม่หาผิดที่
อ้างข้อของ acceptance ในใบงาน
"ขัดกับ acceptance ข้อ 3"		 บังคับให้ QA ตีกลับได้เฉพาะสิ่งที่ใบงานเรียกร้องจริง — ตัดต้นตอของการตีกลับไม่จบด้วยรสนิยมส่วนตัว. ถ้าอ้างข้อไหนไม่ได้ = ไม่ใช่เหตุให้ตีกลับ
severity: blocking / non-blocking เฉพาะ blocking เท่านั้นที่ตีใบกลับได้. non-blocking ไปลง proposed[] — ไม่งั้นเรื่องจุกจิกจะทำให้ใบวนไม่จบทั้งที่งานหลักถูกแล้ว
หลักฐานที่รันได้
คำสั่ง + output ที่แดง		 แยก "ตรวจเจอจริง" ออกจาก "รู้สึกว่าน่าจะพัง" — dev จะได้ไม่ไล่แก้ผี
กับดัก 1 — ละเอียดจนกลายเป็นสั่งวิธีแก้: ถ้า finding เขียนว่า "ให้เปลี่ยนบรรทัด 48 เป็น x ?? y" QA ก็คือคนเขียนโค้ดผ่านมือ dev แล้วมาตรวจงานที่ตัวเองสั่ง — bias ที่ QA ถูกสร้างมาเพื่อกำจัด กลับเข้ามาทางประตูหลัง. finding บอกได้แค่ อะไรผิดเทียบกับใบงาน ห้ามบอกว่าต้องเขียนโค้ดยังไง
กับดัก 2 — finding ที่ไม่มีเกณฑ์รองรับ: "โค้ดนี้อ่านยาก" / "น่าจะแยกฟังก์ชัน" อ้าง acceptance ข้อไหนไม่ได้ = ไม่ใช่ blocking. ของแบบนี้ลง proposed[] ให้ต่องตัดสินทีหลัง. นี่คือกลไกที่กันไม่ให้ QA ตีกลับด้วยรสนิยมจนงานไม่เดิน

5 · รันยังไง

ต่องพูดถึง "qa queue loop" เป็น loop แยก — แนะให้เริ่มที่ loop เดียวสลับ 2 บทบาทก่อน:

แนะให้เริ่มแบบนี้

1 loop · 2 บทบาท

ทุก tick: เคลียร์คิว in_review ก่อน (สวมหมวก QA) แล้วค่อยหยิบงาน dev ใบใหม่

ได้: ไม่มี race · state ที่เดียว · debug ง่าย · fresh context ได้จากการ spawn subagent สำหรับ QA

เสีย: ไม่ขนาน — แต่ WIP=1 อยู่แล้วเลยไม่ได้เสียอะไรจริง

ยังไม่ต้อง

2 loop แยกเซสชัน

dev loop กับ qa loop วิ่งพร้อมกันคนละหน้าต่าง

ต้องมีก่อน: atomic write (tmp+rename) · one-writer-per-status · หลักฐานว่า QA เป็นคอขวดจริง

ความเสี่ยง: lost update บน queue.json แบบเงียบ ๆ — เจอตอนงานหายไปแล้ว

Fresh context ได้จากไหนถ้าอยู่ loop เดียว

ตอนถึงคิว QA ให้ spawn subagent ที่ได้รับแค่ 3 อย่าง: ใบงาน (JSON), diff ของ PR, และคำสั่ง acceptance — ไม่ส่ง transcript ของตอนเขียนโค้ดไปด้วย. subagent คืนมาแค่ verdict + findings. นี่คือ fresh context จริงในทางปฏิบัติ และเป็น pattern เดียวกับที่ sd-curator ใช้อยู่ (read-only, คืนผลอย่างเดียว)

tick: อ่าน state
  ├─ มีใบ in_review?  → spawn QA subagent (ใบ+diff เท่านั้น)
  │                     ผ่าน → ready_for_human + gh pr ready
  │                     ไม่ผ่าน → rework + findings
  │                     wakeup 60s (มีของทำต่อ)
  ├─ ไม่มี → หยิบ rework ก่อน todo   ← ของค้างมาก่อนของใหม่
  └─ ไม่มีทั้งคู่ → สรุป + stop
ลำดับความสำคัญในคิว: rework ต้องมาก่อน todo เสมอ ไม่งั้นใบที่โดนตีกลับจะถูกดองไว้ท้ายแถวขณะที่ loop ไปเปิดงานใหม่เรื่อย ๆ — จบลงที่ PR ค้างครึ่ง ๆ กลาง ๆ เต็มไปหมด (WIP สูงคือศัตรูของทุก queue system)

6 · Skill grooming — /groom

อันนี้เห็นด้วยเต็มที่ และมองว่าสำคัญกว่า QA loop. เหตุผลตรงไปตรงมา: จากที่วางไว้ในเอกสารก่อน คุณภาพของ loop = คุณภาพของคิว. QA loop คือการจับของเสียที่ปลายทาง ส่วน grooming คือการไม่ให้ของเสียเข้ามาตั้งแต่ต้นทาง — ถูกกว่าและได้ผลกว่ามาก

6.1 สิ่งที่ skill นี้ต้องไม่เป็น

ห้ามเป็นตัวแปลงอัตโนมัติ. ถ้า /groom รับ req กำกวมแล้ว "เติมช่องที่ขาดให้เอง" มันคือการเดา design แล้วประทับตราว่าใบนี้ผ่านเกณฑ์ — queue poisoning ที่แนบเนียนกว่าเดิม เพราะตอนนี้ใบปลอมมีหน้าตาถูกต้องครบทุกช่อง. หน้าที่ของมันคือถามจนครบ หรือปฏิเสธ ไม่ใช่เติมเอง

6.2 การทำงาน

  1. รับ req จากอะไรก็ได้พิมพ์สด · ข้อความ Linear · fleeting note · screenshot (OCR) · ผล QA ที่เด้ง needs_attention
  2. แตกเป็นใบย่อยที่ทำจบได้ใน 1 tickreq ก้อนใหญ่ = หลายใบ + depends_on ระหว่างกัน. ใบที่ประเมินว่าใหญ่เกิน 1 tick ต้องแตกต่อ
  3. Classify tier แบบ keyword/pathแตะ schema/API/CI → L2 · แตะ secret/RBAC/payment/PII/prod → L3 ไม่เข้าคิว ตัดออกตั้งแต่ตรงนี้เลย · ไม่ชัด = เด้งขึ้นเลนสูงกว่า
  4. ตรวจ 4 เกณฑ์ ticket contractacceptance ที่เครื่องตรวจได้ / ไม่มี design ค้าง / blast radius รู้ / ย้อนได้
  5. ช่องที่ขาด = ถามต่อง ทีละคำถามที่ตอบง่าย"acceptance ของใบนี้คือคำสั่งไหน" ไม่ใช่ "ช่วยอธิบายเพิ่ม". ถ้าต่องไม่ตอบ/ตอบไม่ได้ = ใบนั้นยังไม่พร้อม จบ
  6. เขียนออก 2 ทางผ่านครบ → queue.json · ไม่ผ่าน → needs_grooming.md พร้อมระบุว่าขาดข้อไหน · L3 → escalations

6.3 Output ที่ควรได้ทุกครั้ง

/groom "แก้ dep GHSA-r28c ทั้ง acme-app กับ lawyer-app แล้วก็อยากให้ auth ดีขึ้นด้วย"

→ เข้าคิว 2 ใบ
   q1  acme-app: override dep + build/typecheck ผ่าน          L2
   q2  lawyer-app: override dep + build ผ่าน               L2  (base=main → PR only)
→ ไม่เข้าคิว 1 ใบ
   "auth ดีขึ้น" — ขาด: acceptance, design ยังไม่เคาะ,
   blast radius ไม่รู้, แตะ auth = อาจ L3
   → needs_grooming.md  (ถามกลับ 2 ข้อ)
ตัวชี้วัดของ skill นี้: ดูที่ first-pass rate ของใบที่มันปล่อยผ่าน. ถ้าใบที่ groom แล้วยังโดน QA ตีกลับบ่อย แปลว่าเกณฑ์หย่อนเกิน — ต้องไปรัดที่ /groom ไม่ใช่ไปโทษ dev loop. เกณฑ์การคัดคือของที่ควรจะแน่นขึ้นเรื่อย ๆ ตามที่เจอเคสจริง

7 · ลำดับที่ควรทำ

  1. /groom ก่อน เริ่มที่นี่ ให้ค่าทันทีแม้ยังไม่มี loop อะไรเลย — แค่มีคิวที่เขียนดีก็ช่วยงานมือได้แล้ว และเป็น input ที่จำเป็นของทุกอย่างที่ตามมา. ยังไม่ต้องรอ dev loop
  2. dev loop เดี่ยว จบที่ ready_for_human ยังไม่มี QA — dev-side acceptance + autoreview แล้วเปิด draft PR ให้ต่องดูเอง. รอบนี้คือการวัดว่า first-pass rate จริงเท่าไร ถ้าสูงอยู่แล้ว QA loop อาจไม่จำเป็น ประหยัดไปเลย
  3. เพิ่ม QA เป็นบทบาทที่ 2 ใน loop เดิม ทำเมื่อข้อ 2 บอกว่า first-pass ต่ำกว่า 70% จริง. ใช้ subagent เป็น fresh context ตามส่วนที่ 5
  4. แยกเป็น 2 loop ต่อเมื่อวัดได้ว่า QA เป็นคอขวด — และตอนนั้นต้องมี atomic write + one-writer-per-status ก่อน
เหตุผลที่ไม่ทำ QA loop พร้อมกันเลย: QA loop เพิ่มต้นทุนทุกใบและเพิ่มจุดพังใหม่ 5 จุดตามส่วนที่ 2. ถ้า first-pass rate ของ dev loop สูงพออยู่แล้ว มันคือการจ่ายเพื่อแก้ปัญหาที่ยังไม่มี. วัดก่อนแล้วค่อยเพิ่ม — และเราจะรู้ตัวเลขนั้นภายในรอบเดียว
