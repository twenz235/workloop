Orchestrated Loops

2 loop แยกเซสชันเด็ดขาด + orchestrator ที่ปล่อย worker หลายตัวทำหลายการ์ดพร้อมกัน และเติม worker เองเมื่อการ์ดเพิ่ม

คำตอบของโจทย์ concurrency: ไม่ใช้ lock เลย — ใช้ ownership by location + atomic rename. แต่ละสถานะเป็นโฟลเดอร์ที่มีเจ้าของคนเดียว การ์ดคือไฟล์ที่ถูก mv ข้ามโฟลเดอร์ ซึ่งบน filesystem เดียวกันเป็น operation ที่แบ่งไม่ได้. ผลคือ สอง loop ไม่เคยเขียนไฟล์เดียวกันเลยแม้แต่ครั้งเดียว — ตรงกับที่ต่องต้องการว่า "ไม่ให้ร่วมกันเลย" โดยไม่ต้องแลกกับความถูกต้อง

1 · อะไรเปลี่ยนไป

การขนานทำให้ invariant เดิม 2 ข้อใช้ไม่ได้ ต้องมีของมาแทนแบบตรงตัว ไม่ใช่แค่ยกเลิก:

ดีไซน์เดิมตอนนี้ของที่มาแทน
WIP = 1 — กัน diff ปนกัน ตายแล้ว (ขนาน N ใบ) worktree isolation — worker แต่ละตัวได้ git worktree ของตัวเอง ไฟล์ไม่ชนกันระดับ filesystem + conflict-set กันการ์ดที่แตะไฟล์เดียวกันไม่ให้รันพร้อมกัน
คิวว่าง = stop ตายแล้ว (ต้องรอการ์ดใหม่) idle mode — คิวว่าง = noop + backoff จนชน 3600s รอการ์ดใหม่ · จบด้วย deadline หรือ STOP เท่านั้น
queue.json ไฟล์เดียว ตายแล้ว (2 writer) 1 การ์ด = 1 ไฟล์ ย้ายข้ามโฟลเดอร์สถานะ
loop เติมการ์ดเองไม่ได้ ยังอยู่ — ยังเป็นกฎเหล็ก. การ์ดใหม่มาจาก /groom เท่านั้น
loop ไปได้สูงสุดแค่ PR ยังอยู่ — ขนานแล้วยิ่งต้องคุม

1.1 orchestrator ไม่ต้องเป็น agent อีกชั้น

ต่องบอกว่า "ให้ loop สร้าง orchestra multi-agent" — ผมออกแบบให้ tick ของ loop เองคือ orchestrator ไม่แทรก agent ชั้นกลางเพิ่ม เหตุผล:

  • agent ชั้นกลางจบเทิร์นแล้วหายไป → ต้อง spawn ใหม่ทุก tick อยู่ดี = ไม่ได้ความต่อเนื่องอะไรเพิ่ม แต่จ่ายค่า spawn ทุกรอบ
  • state ต้อง sync ข้ามชั้นเพิ่มอีกหนึ่งชั้น = จุดพังเพิ่มโดยไม่ได้ประโยชน์
  • เหตุผลเดียวที่คนอยากมีชั้นกลางคือ "ไม่ให้ tool output ท่วม context" ซึ่ง worker แบบ background แก้ให้อยู่แล้ว — ผลของ worker ไม่เข้า context ของ orchestrator

orchestrator จึงเป็นแค่ ผู้จ่ายงานกับผู้เก็บผล และมีข้อห้ามสำคัญ: มันห้ามลงมือแก้โค้ดเองเด็ดขาด แม้ใบเดียว. ทันทีที่มันลงมือ context มันจะบวมด้วยรายละเอียดของงานใบนั้น แล้วการตัดสินใจจ่ายงานใบอื่นจะแย่ลงทั้งกระดาน

2 · Concurrency model

โจทย์: dev loop กับ qa loop อยู่คนละเซสชัน มองไม่เห็นกัน แต่ต้องส่งงานหากันโดยไม่มีอะไรหายหรือถูกทำซ้ำ

2.1 หลักการเดียวที่ทั้งระบบตั้งอยู่บนมัน

หลัก 1

Ownership by location

แต่ละโฟลเดอร์สถานะมี เจ้าของคนเดียว ที่มีสิทธิ์หยิบการ์ดออกและแก้เนื้อใน

todo/ rework/ → dev เท่านั้น
in_review/ → qa เท่านั้น

ไม่มีจุดไหนที่สอง loop แย่งการ์ดใบเดียวกัน — กันด้วยโครงสร้าง ไม่ใช่ด้วยการล็อก

หลัก 2

Atomic rename = claim

จะทำงานใบไหนต้อง mv มันเข้าโฟลเดอร์ claim ของตัวเองก่อน

rename บน filesystem เดียวกันแบ่งไม่ได้ — แย่งกันสองตัว มีตัวเดียวสำเร็จ อีกตัวได้ error แล้วไปหยิบใบอื่น

ไม่มี stale lock ให้ต้องเก็บกวาด มีแต่ไฟล์ค้างที่ reconcile ได้

# claim ที่ปลอดภัย — ใช้ noclobber แล้วยืนยันว่าต้นทางหายจริง
mv -n queue/todo/q7.json queue/claimed-dev/q7.json
test ! -e queue/todo/q7.json || { echo "แพ้การแย่ง ไปใบอื่น"; }
เงื่อนไขที่ทำให้ atomic จริง: ทุกโฟลเดอร์ต้องอยู่ ใน filesystem เดียวกัน (volume เดียว). ถ้าข้าม volume, mv จะกลายเป็น copy+delete ซึ่งไม่ atomic และจะมีช่วงที่การ์ดอยู่ทั้งสองที่. อย่าวาง state ไว้บน iCloud Drive / network drive เด็ดขาด — ~/.claude/loops/ บนดิสก์เครื่องเท่านั้น

2.3 ทำไม /groom เขียน todo/ ได้ทั้งที่ dev เป็นเจ้าของ

เพราะมันสร้างไฟล์ใหม่ชื่อใหม่ ไม่เคยแก้ไฟล์ที่มีอยู่. การสร้างไฟล์ที่ยังไม่มีกับการหยิบไฟล์ที่มีอยู่ ไม่ชนกันแม้จะทำพร้อมกัน. ข้อบังคับเดียวคือ เขียนแบบ tmp แล้ว rename — ไม่งั้น dev อาจหยิบไฟล์ที่เขียนค้างครึ่งใบไปทำ:

echo "$card" > queue/.tmp/q9.json && mv queue/.tmp/q9.json queue/todo/q9.json

กฎเดียวกันนี้ใช้กับทุกครั้งที่มีการเขียนเนื้อการ์ด (QA เขียน findings ก็ต้อง tmp+rename เหมือนกัน)

4 · Orchestrator tick

ทั้งสอง loop ใช้โครงเดียวกัน ต่างกันแค่โฟลเดอร์ที่เป็นเจ้าของกับชนิดของ worker:

  1. STOP + budget guardมี STOP → หยุด (สั่ง worker ที่วิ่งอยู่ให้จบ แล้วคืนการ์ด). เลย deadline หรือหมด token budget → เหมือนกัน
  2. Reconcile ของค้างการ์ดใน claimed-* ที่ claimed_at เก่ากว่า 30 นาที และไม่มี worker ไหนถืออยู่ → ไปดูความจริงที่ git (branch/diff มีไหม) แล้วคืน todo/ หรือส่ง needs_attention/
  3. Harvest ผลของ worker ที่จบอ่าน verdict ที่ worker เขียนไว้ในการ์ด → mv ไปโฟลเดอร์ถัดไป. อ่านผลสรุปเท่านั้น ไม่ดึง transcript ของ worker เข้ามา
  4. เช็ค backpressureถ้าของกองตรงกลางเกินเพดาน (ส่วนที่ 6) → ข้ามขั้น dispatch ไปเลย ไม่ spawn เพิ่ม
  5. Dispatch เติมช่องว่างslots = max_workers − running · เลือกการ์ดจาก rework/ ก่อน todo/ ที่ conflict-free กับที่กำลังรัน · claim ด้วย mv · spawn worker แบบ background พร้อม worktree แยก
  6. Persist แล้วค่อยตั้งเวลาตื่นเขียน runtime/*.json + append journal ก่อน ScheduleWakeup เสมอ

เลือกเวลาตื่นยังไง

สภาพdelaynoopเหตุผล
มี worker วิ่งอยู่1200–1800trueworker จบเมื่อไรระบบปลุกให้เอง — นี่เป็นแค่ตาข่ายกันแฮงก์
มี slot ว่าง + มีการ์ดรอ60falseไม่ได้รออะไร รีบจ่ายงานต่อ
คิวว่าง (idle)300 → ×2 → 3600trueรอ /groom ใส่การ์ดใหม่ ยิ่งเงียบนานยิ่งเช็คห่าง
backpressure เต็ม900trueรอคนเคลียร์ PR — เร่งไปก็ไม่มีประโยชน์

5 · Conflict-set scheduling

worktree แยกกันแก้ปัญหาไฟล์ชนกันตอนเขียนได้ แต่ไม่ได้แก้ปัญหาตอนmerge: การ์ดสองใบที่แก้ไฟล์เดียวกันคนละ worktree จะได้ PR สองอันที่ conflict กันแน่นอน แล้วใครก็ตามที่ merge ทีหลังต้องมานั่ง rebase — ซึ่งเป็นงานที่ loop ทำไม่ได้

ทางแก้: ใช้ฟิลด์ touches ในการ์ด (ที่ /groom บังคับให้ระบุอยู่แล้ว) เป็น ชุดกุญแจล็อก. การ์ดจะถูก dispatch ได้ก็ต่อเมื่อ touches ของมันไม่ตัดกับtouchesของทุกใบที่กำลังรันอยู่. นี่ทำให้ฟิลด์ที่ดูเป็นเอกสารเฉย ๆ กลายเป็นกลไกจริงของ scheduler 
running: q1{package.json, pnpm-lock.yaml}  q2{src/utils/date.ts, …test.ts}

พิจารณา q5{src/utils/date.ts}      → ตัดกับ q2 → ข้าม รอรอบหน้า
พิจารณา q6{src/api/user.ts}        → ไม่ตัดกับใคร → dispatch ได้
พิจารณา q7{package.json}           → ตัดกับ q1 → ข้าม
  • Glob ให้หยาบไว้ก่อน — touches: ["src/api/**"] ปลอดภัยกว่าไล่ระบุทีละไฟล์แล้วพลาด. เสียความขนานนิดหน่อย แลกกับไม่ต้อง rebase มือ = คุ้ม
  • ไฟล์ร้อนต้อง serialize เสมอ — package.json, lockfile, migration, schema, config กลาง. ประกาศเป็น hot_paths ในคอนฟิก: การ์ดที่แตะไฟล์เหล่านี้บังคับรันเดี่ยว ห้ามมีอะไรขนานด้วยเลย
  • Starvation guard — การ์ดที่ถูกข้ามเกิน 5 รอบเพราะ conflict ให้เลื่อนเป็นคิวหน้าสุดครั้งถัดไป ไม่งั้นใบที่แตะไฟล์ยอดนิยมจะไม่ได้ทำสักที

6 · Dynamic scaling + backpressure

โจทย์ของต่อง — "การ์ดเพิ่มก็สร้าง agent เพิ่มได้เลย" — ทำได้ตรง ๆ ด้วย worker pool ที่เติมช่องว่างทุก tick โดยไม่ต้องรีสตาร์ทอะไร:

  1. /groom หย่อนการ์ดใหม่ลง todo/ ตอนไหนก็ได้แม้ตอน loop กำลังวิ่ง — เพราะเป็นการสร้างไฟล์ใหม่ ไม่ชนกับใคร
  2. tick ถัดไปเห็นเองorchestrator นับ slot ว่าง แล้วหยิบเท่าที่ conflict-free — ไม่ต้องบอก ไม่ต้องรีสตาร์ท
  3. worker จบ = ระบบปลุก orchestrator ทันทีเติม slot ต่อได้เลยโดยไม่ต้องรอครบรอบ — สำคัญ เพราะแบบ batch จะเสียเวลาไปกับการรอ worker ที่ช้าที่สุดของรอบเสมอ

เพดานที่ต้องตั้ง — ทุกตัวมีเหตุผลของมัน

เพดานค่าเริ่มถ้าไม่มีจะเกิดอะไร
dev.max_workers3token burn ขนานไม่มีเพดาน + CI คิวยาว
qa.max_workers2QA เบากว่า (read-only) แต่ก็กิน token
max_in_flight5สำคัญสุด — dev ผลิตเร็วกว่า QA ตรวจ ของกองที่ in_review/ ไม่มีที่สิ้นสุด
max_open_prs3PR ท่วมจนคนรีวิวไม่ทัน = คอขวดย้ายไปอยู่ที่คน
token_budgetต่อ loop ต่อวันขนาน N ตัว = เผาเร็วขึ้น N เท่า รู้ตัวอีกทีตอนเช้า
deadline_atต่อ loopidle mode ไม่มีวันจบเองเพราะออกแบบให้รอการ์ดใหม่
Backpressure คือสิ่งที่คนมักลืม: พอ dev ขนาน 3 ตัวแต่ QA ขนาน 2 ตัว ระบบจะผลิตเร็วกว่าตรวจโดยธรรมชาติ. ถ้าไม่มี max_in_flight ของจะกองที่ in_review/ เรื่อย ๆ — worker ยังทำงานหนัก ตัวเลขดูสวย แต่ไม่มีอะไรถึงมือต่องเร็วขึ้นเลย เพราะคอขวดอยู่ปลายทาง. เมื่อชนเพดาน dev ต้องหยุดรับงานใหม่ ไม่ใช่ทำต่อ

7 · Worker contract

dev worker

เขียนโค้ดได้ · worktree แยก

ได้รับ: การ์ด 1 ใบ + path ของ worktree

ทำ: แก้ → acceptance ทุกข้อ → autoreview → push + draft PR

คืน: verdict + branch + PR + ผลเทสตามจริง (แดงต้องบอกว่าแดง)

ห้าม: merge · แตะไฟล์นอก touches · เพิ่มการ์ดใหม่ · แตะ L3

qa worker

read-only · fresh context

ได้รับ: การ์ด + diff ของ PR + คำสั่ง acceptance — ไม่มี transcript ของ dev

ทำ: build/integration เต็ม + regression + ไล่ acceptance ทีละข้อ + จับ scope drift

คืน: pass หรือ findings ที่มี file:line + violates + severity

ห้าม: แก้โค้ด · merge · ตีกลับด้วยเหตุผลที่อ้าง acceptance ไม่ได้

ทำไม worker ต้องเป็น background: ผลลัพธ์ระหว่างทางของมันจะไม่เข้า context ของ orchestrator — orchestrator เห็นแค่สรุปตอนจบ. ถ้าไม่ทำแบบนี้ ขนาน 3 ตัวเท่ากับ transcript 3 ชุดไหลเข้า context เดียว แล้ว orchestrator จะโดน compaction ภายในไม่กี่ tick และเริ่มจ่ายงานมั่ว

8 · ปัญหาใหม่ที่การขนานสร้างขึ้น

สูง

8.1  Semantic conflict — CI เขียวตอนเปิด แต่พังหลัง merge

3 PR แตกจาก base เดียวกัน ทุกอันเขียว. merge อันแรกเข้า dev → อีก 2 อันกลายเป็น stale ทันที. ไม่ conflict ที่ระดับ text (คนละไฟล์) แต่พังที่ระดับความหมาย — เช่นใบหนึ่งเปลี่ยน signature ของฟังก์ชัน อีกใบเพิ่ม caller ใหม่ที่เรียกแบบเก่า

แก้: QA ต้องรัน บน merge preview (base ล่าสุด + PR นั้น) ไม่ใช่บน branch เปล่า ๆ · และเมื่อ base ขยับ (มี PR ถูก merge) ให้ mark การ์ดที่ยังไม่ merge ว่า stale แล้วส่งกลับ in_review/ เพื่อ verify ซ้ำ — verify ซ้ำถูกกว่าการ revert เยอะ
สูง

8.2  Worktree รั่ว

worker ตายกลางทาง → worktree ค้าง + branch ค้าง. สะสมข้ามคืนจนดิสก์เต็มและ git worktree list อ่านไม่รู้เรื่อง

แก้: ตั้งชื่อ worktree/branch ด้วย card id เสมอ (loop/q7-…) → reconcile รู้ทันทีว่าอันไหนของใบไหน · ทุก tick เก็บกวาด worktree ที่การ์ดไม่ได้อยู่ใน claimed-* แล้ว · ตอน loop จบให้ git worktree prune
กลาง

8.3  Split-brain ระหว่างสอง loop

ทั้งสอง loop มีมุมมองของตัวเองว่าระบบมีอะไรอยู่บ้าง และมันไม่ตรงกัน — dev คิดว่าส่ง q3 ไป review แล้ว แต่ qa ยังไม่เคยเห็น (เพราะยังไม่ tick)

แก้: ยอมรับว่ามันไม่ตรงกันเป็นเรื่องปกติ — ห้าม loop ไหนตัดสินใจจากสมมติฐานว่าอีกฝั่งทำอะไรไปแล้ว. ตัดสินจากสิ่งที่เห็นในโฟลเดอร์ตัวเองเท่านั้น. ความจริงเดียวของระบบคือ filesystem ไม่ใช่ runtime ของ loop ไหน
กลาง

8.4  การ์ดหายระหว่าง mv (ช่วงเสี้ยววินาที)

ระหว่าง mv การ์ดจะไม่อยู่ในโฟลเดอร์เดิมแล้วแต่ยังไม่ถึงปลายทางในสายตาของ process ที่กำลังลิสต์อยู่ — loop อีกตัวอาจนับยอดผิดชั่วขณะ

แก้: อย่าใช้ยอดนับเป็นเงื่อนไข หยุด ทันที. "คิวว่าง" ต้องเห็นว่าง 2 tick ติด ถึงจะถือว่าว่างจริง — และเรามี idle mode อยู่แล้วเลยไม่มีอะไรเสียหาย
กลาง

8.5  เซสชันเดียวตายเงียบ ระบบครึ่งใบยังเดินอยู่

qa loop ตาย (เครื่อง sleep, หน้าต่างปิด) แต่ dev loop ยังผลิตต่อ → ของกองที่ in_review/ โดยไม่มีใครมาเก็บ กว่าจะรู้ก็เช้า

แก้: แต่ละ loop เขียน last_tick_at ลง runtime/*.json ทุก tick · อีกฝั่งอ่านของเพื่อน (อ่านอย่างเดียว ไม่เขียน) ถ้าเก่าเกิน 2× ช่วงพักสูงสุด → ประกาศว่าอีกฝั่งตาย แล้วหยุดรับงานใหม่ พร้อมรายงาน. ไม่มีข่าว ≠ ข่าวดี
ต่ำ

8.6  ไล่ปัญหายากขึ้นมาก

ขนาน 3 ตัว journal จะสลับกันจนอ่านไม่ออกว่าอะไรเกิดก่อนหลัง

แก้: ทุกบรรทัด journal ขึ้นต้นด้วย [tick][card-id][worker-id] เสมอ · worker เขียน log ของตัวเองแยกไฟล์ journal/workers/q7.md · journal หลักเก็บแค่ transition ของการ์ด ไม่เก็บรายละเอียดงาน

10 · ลำดับที่ควรทำ

  1. วาง layout + /groom เริ่มที่นี่ สร้างโครงโฟลเดอร์ + skill groom ที่เขียนการ์ดแบบ tmp+rename พร้อมฟิลด์ touches ครบ. ยังไม่มี loop อะไรเลยก็ใช้ประโยชน์ได้แล้ว และ touches คือสิ่งที่ scheduler ทั้งระบบพึ่งพา
  2. dev loop · max_workers = 1 พิสูจน์ claim/reconcile/worktree/harvest ให้ทำงานถูกก่อน โดยยังไม่มีความซับซ้อนของการขนาน. ผิดตรงไหนจะเห็นชัดเพราะมีตัวเดียว
  3. ดัน max_workers เป็น 3 + conflict-set ตรงนี้แหละที่ scheduling เริ่มมีผลจริง — ดูว่ามี PR ที่ต้อง rebase มือไหม ถ้ามีแปลว่า touches หยาบไม่พอ
  4. qa loop เซสชันที่สอง เปิดหน้าต่างที่สอง ชี้ที่ state เดียวกัน. เพิ่ม heartbeat check ระหว่างกันตั้งแต่วันแรก (8.5)
  5. จูนเพดาน ปรับ max_in_flight / max_open_prs จากของจริง — ตัวเลขที่ถูกคือตัวเลขที่ทำให้ ไม่มีอะไรกองรอเกินสองสามชั่วโมง ไม่ใช่ตัวเลขที่ทำให้ worker ยุ่งที่สุด
สิ่งที่จะรู้ได้จากขั้นที่ 3 เท่านั้น: ความขนานที่ใช้ได้จริงถูกกำหนดโดย โครงสร้างโค้ดของโปรเจกต์ ไม่ใช่โดยค่าคอนฟิก. repo ที่ทุกงานวิ่งผ่าน package.json หรือไฟล์ config กลางจะขนานได้แค่ 1–2 ตัวจริง ๆ ไม่ว่าจะตั้ง max_workers เท่าไร. ตั้ง 3 ไว้ก่อนแล้ววัดว่า dispatch จริงได้กี่ตัวต่อ tick — ถ้าค่าเฉลี่ยต่ำกว่า 2 ตลอด แปลว่าคอขวดอยู่ที่ touches ที่ซ้อนกัน ไม่ใช่ที่จำนวน worker
